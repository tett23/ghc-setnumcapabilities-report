Chronological record of what was done, what was found, and why decisions
were made. Newest entries at the bottom. Earlier work (before this folder

is under `evidence/`. Times are JST, 2026-10-17 unless stated.

## Background (from the hand-over)

- Symptom: Golem's test suites (GHC 9.10.3, tasty 1.5.4, `-threaded`) hung
  forever on low-CPU Linux CI; all OS threads were waiting inside the RTS.
- Root cause (confirmed with a debug RTS, `+RTS -Ds` traces and gdb):
  `setNumCapabilities` reads `n_capabilities` / `enabled_capabilities`
  before `stopAllCapabilities()` and uses the stale values after it. If
  another call grew the capability array in between, the later call acquires
  all current capabilities but releases only `old_n_capabilities` of them;
  the leaked capabilities keep a dangling `running_task` and the next GC
  waits for them forever.
- Evidence: `evidence/verify-a` (CapRace.hs, 198/200 hangs on a 10-core Mac,
  163/200 in a 2-CPU container; serialised / decrease-only / no-op controls
  never hang), `evidence/verify-b` (SetCapsRace.hs, CI log analysis),
  `evidence/plugin-test-repro`, `evidence/tasty-pure-repro`.
- Golem itself was fixed downstream (tett23/golem#174: link tests with
  `-with-rtsopts=-N`, stop calling `setNumCapabilities`).

## 16:20 Verifying the fix without building GHC (`evidence/rts-fix-check/`)

- Idea: the fix touches one file, so compile `rts/Schedule.c` alone and
  swap it into copies of the shipped `libHSrts-1.0.2_thr.a` and
  `_thr_debug.a` of ghcup's GHC 9.10.3.
- Flags were reconstructed from hadrian / rts.cabal (`-DCOMPILING_RTS
  -DFS_NAMESPACE=rts -DTHREADED_RTS -fno-strict-aliasing -fno-common
  -fwrapv`, `-O2` for `thr`, `-O0 -g -DDEBUG` for `thr_debug`), with the
  9.10.3 source tree from `git archive` and the installed
  `rts-1.0.2/include` for the generated headers. Check: compiling the
  *unmodified* file gives objects whose defined and undefined symbol sets
  equal the shipped `Schedule.thr_o` / `Schedule.thr_debug_o`.
- Mistake and correction: the first link used `-optl-L<dir>`. GHC appends
  `-optl` flags after the package `-L` directories, so the shipped RTS was
  linked both times and the "fixed" reproducer still hung 50/50. Noticed
  because `otool -tV` showed the same `setNumCapabilities` code in both
  binaries (172 instructions, versus 180/201 in the recompiled objects).
  GHC's own `-L<dir>` flag goes first and, with `-search_paths_first`,
  makes the swapped archive win. From then on every binary is checked with
  the `otool` instruction count before it is measured.
- Results with the swap done correctly (`RESULTS.md`): the reproducer
  hangs 20/20 with the original object and 0/50 with the fix; the test
  candidate (rounds=3, setters=4) fails 20/20 (threaded2) and 8/10
  (threaded1) unfixed, passes 100/100 in threaded2 fixed, but 49/50 in
  threaded1 fixed: one run exceeded the 60 s watchdog while still using
  CPU. That is the slow-GC-with-many-capabilities behaviour already seen
  in verify-a (13 capabilities on 10 cores), not the leak, but it would
  make the test fragile.
- Decision: shrink the test so that the capability count stays small.
  Three variants are being measured (rounds×setters = 2×3, 3×2, 1×4;
  caps up to base+6 or base+4), each unfixed 10 runs per way (watchdog
  shortened to 20 s for speed) and fixed 60 runs per way with the 60 s
  watchdog. Script: `evidence/rts-fix-check/measure2.sh`; log appended
  below when it finishes.

## 17:05 Smaller test variants measured (`evidence/rts-fix-check/measure2.log`)

- All three shapes still fail reliably unfixed in threaded2 (8/10, 4/10,
  9/10) and the fix never deadlocks (0 idle hangs in 360 runs). But the
  slow tail remains in the debug way even with 5 to 7 capabilities on 10
  cores: r1m4 threaded1 fixed had 3/60 runs over the 60 s watchdog, r3m2
  threaded1 fixed had a 55 s run. So the tail is *not* "more capabilities
  than cores"; the number of capabilities barely matters.
- Also notable: the unfixed "ok" runs take 16 to 20 s on average in the
  variants, i.e. even the runs that do not deadlock are slow, which fits a
  GC-synchronisation slowdown that exists with or without the fix.
- New hypothesis: the slow tail comes from the GC pressure of the worker
  threads (4 workers each calling `performGC` every 400 iterations while
  the capability count changes). Measuring two variants with rounds=3,
  setters=4: `w0` (no workers; only the main thread's `performGC` after
  each round) and `nogc` (workers allocate but never call `performGC`).
  Script: `evidence/rts-fix-check/measure3.sh`.

## 17:25 GC-pressure variants (`evidence/rts-fix-check/measure3.log`)

- `w0` (no worker threads): unfixed fails 10/10 in both ways; fixed passes
  60/60 in both ways with every run under 0.44 s. `nogc` (workers that
  allocate but never call `performGC`): unfixed 10/10 fails, but fixed has
  9/60 and 5/60 runs over 60 s. So the worker threads are the cause of the
  slow tail, and GC pressure is not even needed for the leak to show: the
  main thread's `performGC` after each round is enough.
- Decision: the test is the `w0` shape (rounds=3, setters=4, no workers);
  `mr/testsuite/tests/rts/TNNNNN.hs` rewritten accordingly and
  `mr/MR_DESCRIPTION.md` filled with the numbers.
- Side finding for HANDOFF item 2 (the "busy_timeout" mystery): a
  stop-the-world sync from the main thread can take tens of seconds while
  other threads run tight allocating loops, fixed or not, with as few as 5
  capabilities on 10 cores, and it is *worse* when the workers do not call
  `performGC` themselves. That is a separate RTS behaviour worth its own
  investigation (and possibly its own ticket); it is not part of this MR.

## 2026-11-06 15:05 HANDOFF item 2: the slow stop-the-world syncs (`evidence/sync-lag/`)

- Re-read #27460 / #27473 (sync promptness, returning tasks before pending
  sync). Plausible but not specific to what we saw; parked.
- Wrote `SyncLag.hs`: allocating workers, main thread times either
  `performGC` or serial `setNumCapabilities` (n+1 / n alternating). No
  concurrency between `setNumCapabilities` calls, so the leak cannot occur.
  First scan: `performGC` always ~1 ms; `setNumCapabilities` with the `-O`
  build never finishes 50 calls within 120 s at `-N2` or `-N4`; the debug
  build is intermittent (max 0.1–5 s per run). So the phenomenon is specific
  to `setNumCapabilities`.
- Captured a timestamped `+RTS -Ds` trace of a 2.5 s call (debug build).
  The RTS part of the call takes under 1 ms; the rest is the bound helper
  thread for `ioManagerCapabilitiesChanged` (run by `rts_evalIO` at the end
  of `setNumCapabilities`) sitting runnable on the caller's capability while
  a worker thread on the same capability is re-run after every one of its
  300+ stops. Trace excerpts and line references in `RESULTS.md`.
- Code reading: a yielding thread goes to the back of the run queue only if
  `cap->context_switch` is set (`scheduleHandleYield`,
  `scheduleHandleHeapOverflow`); that flag is set by the timer tick, and
  `setNumCapabilities` in 9.10.3 / 9.12.4 / 9.14.1 holds `stopTimer()` from
  before the sync until after the IO-manager notification. Master removed
  the `stopTimer()/startTimer()` pair on 2026-06-12 (341ed474).
- Confirmation 1: `+RTS -C0` (context switch on every scheduler pass,
  timer-independent) turns the `-O` build's >60 s stall into max 58 ms.
- Confirmation 2 in progress: RTS variant `nostop` (the fixed
  `Schedule.c` with the `stopTimer()/startTimer()` pair removed), swapped
  into the 9.10.3 archives like the leak fix (`rebuild-nostop.sh`; the
  scratch build tree had been cleared since the previous session and was
  rebuilt from `evidence/rts-fix-check/patch.py` and `ccrts.sh`).

## 2026-11-06 15:40 Item 2 resolved: the stall is 9.10–9.14's stopTimer around the IO-manager notification

- Confirmation 2 done: the `nostop` RTS variant (leak fix + `stopTimer()`
  pair removed) finishes 50 `setNumCapabilities` calls with max 23–95 ms in
  both builds, while `orig` and `fixed` time out (`-O`) or take seconds
  (debug). Table in `evidence/sync-lag/RESULTS.md`, log `nostop.log`.
- So HANDOFF item 2 is explained: not a deadlock, not "more capabilities
  than cores", not the leak. It is a scheduling starvation: with the timer
  stopped, `scheduleHandleYield` always re-queues the running thread at the
  front, and the bound thread that `setNumCapabilities` starts for
  `ioManagerCapabilitiesChanged` waits behind it until something else
  (a rare GC-driven context switch) lets it in. Master has already removed
  the `stopTimer()` (341ed474), so this is a released-versions-only issue.
- Side effect for the earlier measurements: in verify-a's `serial`/`dec`
  rows and the `rts-fix-check` worker variants, every slow run was this
  mechanism; the worker threads' allocation pattern (how often GC happens)
  decided how long the starvation lasted, which is why removing the workers
  made the testsuite test stable.
- Updated `issue.md`: the "unrelated slow runs" paragraph now states the
  cause and the master commit instead of "not investigated".
- Open decision for tett23: mention it only in the main issue (done), or
  also open a second ticket asking for 341ed474 to be backported to the
  maintained release branches (draft not written yet).
